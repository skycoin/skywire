# skymail-bridge (standalone)

Standalone, dmsg-only SMTP→skywire bridge. Speaks SMTP on a local
TCP port, dials peers via its own `dmsg.Client`, and **does not
require a running visor**. Intended for hosts that bridge a
mailserver's outbound queue onto dmsg without otherwise running
skywire.

For hosts that already run a visor, use the **in-process bridge**
embedded in the visor (`pkg/visor/embedded_skymail_bridge.go`). It
runs in the visor process, reuses the visor's dmsg session, and is
managed via the resolver-style CLI:

```sh
skywire cli mail            # status
skywire cli mail up         # enable
skywire cli mail down       # disable
```

The in-process bridge is configured under `skymail_bridge` in the
visor config (autogenerated by `skywire cli config gen --skymail-bridge`).

Both flavors share the protocol core in `pkg/skymailbridge`. They
differ only in where the dmsg session comes from.

## Address shapes

  - **Mode B (default)** — `user@<host>.<base32-pk>.skynet`
    → bridge strips `.<pk>.skynet` from RCPT TO before forwarding.
    Receiver's existing virtual_alias / mydestination chain works
    unchanged.
  - **Mode A** — `user@<base32-pk>.skynet` → forwarded verbatim.
    Receiver's Postfix must accept `<pk>.skynet` in mydestination.

PubKey is encoded as a lowercase RFC 4648 base32 label (53 chars —
fits in a single 63-octet DNS label per RFC 1035 §2.3.1). Helpers
live in `pkg/cipher` as `PubKey.DNSLabel()` / `ParseDNSLabel`.

## Usage

```sh
# Persistent identity recommended. Provide via --sk, --sk-file, or
# $SKYMAIL_SK; otherwise an ephemeral keypair is generated per
# launch (PK won't match any receiver's allowlist across restarts).
export SKYMAIL_SK="<hex-secret-key>"

skymail-bridge \
  --addr        127.0.0.1:1025 \
  --mode        b \
  --suffix      .skynet \
  --remote-port 25
```

Then add to Postfix `main.cf`:

```
transport_maps = lmdb:/etc/postfix/transport
```

And `/etc/postfix/transport`:

```
.skynet  relay:[127.0.0.1]:1025
```

After `postmap` + reload, mail addressed to `user@…<pk>.skynet`
routes through the standalone bridge over dmsg to the peer.

## Receiver side

Identical regardless of which sender flavor (standalone or
in-process) is used: the receiver exposes its local Postfix smtpd
on the visor's dmsg face:

```sh
skywire cli serve add 25 --to 127.0.0.1:25 --label skymail-bridge
skywire cli serve whitelist 25 <allowed-sender-pk>,<other-pk>
```

In Mode B no Postfix-side changes are needed — the bridge strips
the suffix before the envelope reaches the receiver's MTA.

## Out of scope

  - STARTTLS on either hop. Local Postfix submission stays plain;
    the cross-wire hop is dmsg-encrypted end-to-end.
  - SMTP AUTH at the bridge inbound side (auth happens at MUA →
    sender's Postfix, before the bridge).
  - Multi-peer envelopes (returns 451 on the second RCPT so Postfix
    retries per-recipient).
  - Sender-side spam filtering — receiver enforces via the standard
    `skywire cli serve whitelist`.

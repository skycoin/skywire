# Gate G6 — M6 Calls
Reviewer: fresh session 2026-10-04   Author: MohammadReza P.
SHA: 7c8aa9a1d   PRs: https://github.com/skycoin/skywire/pull/5309   Date: 2026-10-04
Verdict: FAIL

Calls ring, connect, hold and hang up in both directions, but no audio
crosses an iOS call. The iOS core never runs its voice manager in bridge
mode, so it substitutes silence and refuses the app's microphone and
speaker streams with 503. The suites pass because both audio tests run
against a fake visor. Separately, 15 of the call screen's 18 strings are
missing from the catalog and show as raw keys.

## Criteria

- [ ] "place and receive a call Simulator ↔ Android emulator" — signalling works both ways, **audio does not**.
  - iOS→Android: the screen shows "Pixel8a" from the address book. The
    status goes connecting, then ringing. Android rang, answered, both
    visors logged `call established`, and the timer ran from 0:08.
  - Android→iOS (app in the foreground): iOS rang 15 s after the tap. It
    showed "Pixel8a", "Incoming call" and the suspended-ring note in
    English. Answer connected in about 1 s.
  - Audio: at every connect the iOS core logs
    `WARN [voice]: voice: audio capture unavailable — using silence (call still connects) error="voice: live audio capture/playback not supported on this platform yet (Linux/PulseAudio only)"`.
    The app's `POST /api/voice-audio/{pk}/mic` and
    `GET /api/voice-audio/{pk}/speaker` were answered 503 ("this visor
    uses its own audio device") 2,832 times over the run, about four per
    second per call. Not one stream opened.
  - Cause: `voiceAudioMode()` (pkg/visor/init_voice.go:39) defaults to
    bridge only when `runtime.GOOS == "android"`. Nothing in ios/ sets
    `SKYWIRE_VOICE_AUDIO`, and M6 changed no Go. So the iOS visor has no
    `voiceAudio` bridge (hypervisor_handlers_voice_audio.go:69).
  - VoiceAudioReleaseTests and VoiceEndpointTests both run against a fake
    visor that accepts the streams, so neither can see this.
- [ ] "mute/unmute" — the button toggles its icon and state, and the request goes out. That Android stops hearing iOS cannot be shown, because Android never hears iOS.

## Non-blocking notes

1. A system output client, `CA_UISoundClientBase`, starts with the app's
   first tone and keeps the Simulator output device running for the life
   of the process. It started with the ringback in the first launch and
   with the incoming ring in a fresh one, and stayed through every
   hangup. It is not one of M6's engines. Whether a device keeps the
   audio session or the background-audio keep-alive up because of it is
   unknown. Worth a look on a device.
2. With bridge mode missing, the capture loop restarts the microphone
   about twice a second for the whole call: the input client starts and
   stops, each run about 13 ms. On a device that is a flickering mic
   indicator. Once the bridge exists this path only matters when the
   visor refuses, so a backoff would be kinder.
3. Unanswered backgrounded calls end differently on the caller. One
   showed `failed: read invite reply: EOF` after 45 s, another
   `no_answer` after 58 s.
4. VoiceCalls keeps one `pendingAnswer`. A second answer request that
   lands while the collector is still waiting on the first is cleared by
   the first's `answerHandled()`. This needs two answer taps within the
   15 s wait, so it is an edge case. I did not check Android for the same
   shape.
5. Audio playing in the background from a ring (`CallTones.playRing`
   from the watcher) took a RunningBoard audio power assertion. That is
   fine, but it is another thing that keeps a backgrounded app awake.
6. The XCUITest harness relied on `UITargetAppPath` pointing at the
   runner, so that a runner restart never reinstalled and killed the app
   mid-call. Useful for whoever re-reviews.
7. The release test's "fails without the grant" message was not
   re-checked. The run was stopped to keep the review short.

On re-review: the failed criteria are audio both ways, mute, audio after
backgrounding, the strings, and the backgrounded ring (as far as the
Simulator allows). A smoke of the rest is enough. Bridge mode on iOS will
need a test that runs against the real core, not the fake visor.

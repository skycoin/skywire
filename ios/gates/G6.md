## Non-blocking notes

1. A system output client, `CA_UISoundClientBase`, starts with the app's
   first tone and keeps the Simulator output device running for the life
   of the process. It started with the ringback in the first launch and
   with the incoming ring in a fresh one, and stayed through every
   hangup. It is not one of M6's engines. Whether a device keeps the
   audio session or the background-audio keep-alive up because of it is
   unknown. Worth a look on a device.
2. With bridge mode missing, the capture loop restarts the microphone
   about twice a second for the whole call: the input client starts and
   stops, each run about 13 ms. On a device that is a flickering mic
   indicator. Once the bridge exists this path only matters when the
   visor refuses, so a backoff would be kinder.
3. Unanswered backgrounded calls end differently on the caller. One
   showed `failed: read invite reply: EOF` after 45 s, another
   `no_answer` after 58 s.
4. VoiceCalls keeps one `pendingAnswer`. A second answer request that
   lands while the collector is still waiting on the first is cleared by
   the first's `answerHandled()`. This needs two answer taps within the
   15 s wait, so it is an edge case. I did not check Android for the same
   shape.
5. Audio playing in the background from a ring (`CallTones.playRing`
   from the watcher) took a RunningBoard audio power assertion. That is
   fine, but it is another thing that keeps a backgrounded app awake.
6. The XCUITest harness relied on `UITargetAppPath` pointing at the
   runner, so that a runner restart never reinstalled and killed the app
   mid-call. Useful for whoever re-reviews.
7. The release test's "fails without the grant" message was not
   re-checked. The run was stopped to keep the review short.

On re-review: the failed criteria are audio both ways, mute, audio after
backgrounding, the strings, and the backgrounded ring (as far as the
Simulator allows). A smoke of the rest is enough. Bridge mode on iOS will
need a test that runs against the real core, not the fake visor.

## Non-blocking notes

1. **The call timer shows the previous call's time at connect.** `CallModel.sync` starts from `var next = ui`, which carries `elapsed` over. `connectedAt` is reset, but `elapsed` is not until the first tick, so for up to a second the timer reads the last call's final value ("1:01", "2:48", "4:32" were seen). Resetting `elapsed` when `connectedAt` is set would fix it.
2. **A core that has been up for hours across a host sleep.** The app had run about 10.5 h with the Mac asleep overnight.
   - Its next two calls (A3 to the freshly started emulator, P1 to the fresh desktop peer) were "established" but carried exact silence both ways.
   - They dropped at 2:16 and 0:51 with `media transport failed`, then `could not reconnect … dmsg error 202 - cannot connect to delegated server`.
   - The iOS core also logged `Failed to accept transport … settlement handshake failed`.
   - Relaunching the app fixed it: the same network then held P2 for 4:35.
   - A simulated process across host sleep is not a phone scenario, but worth a device look (Lane D). The call screen ran its timer through the silent calls, and nothing told the user that no audio was arriving.
3. **iOS's hang-up reached Android only through the reconnect timeout in B2.**
   - Android logged `media transport failed` 0.5 s after the iOS tap, before the iOS core's `hung up here` line.
   - It ended 32 s later with `peer hung up` once its resume gave up (dmsg 202).
   - The same hang-up to the desktop peer ended in 0.4 s twice. The first review saw 14 s once.
   - It looks like the core's hang-up signal racing the media close on a slow dmsg path; not iOS-specific.
4. **The Android emulator is not a reliable audio source on this Mac.**
   - The host-mic feed stalls once the Simulator's call capture runs.
   - The emulator also aborted twice. One abort was exit 134 right after `Netsim Wifi … is gone due to Stream removed (recvmsg:Operation timed out (60))`; the other left no log.
   - For the playbook's §5: the desktop lite peer with a tone pushed into its mic stream gives an exact Android-free measure of both iOS directions.
5. **The same unanswered situation ends either way.** "Call failed" (`read invite reply: EOF`, the English run) and "No answer" (Chinese, Spanish) both appeared for unanswered calls to the same desktop peer, as in the first review's note 3.
6. **The system output client (first review note 1) is unchanged.** It starts about 0.1 s after each hang-up and plays zeros.
7. **xcodebuild sits in `simctl diagnose` for about 10 minutes after the tests on this Mac,** with and without `-resultBundlePath`. A bench quirk; the tests had finished.
8. **The operator's first beep confirmation is discounted.** The first version of the reviewer's tap tool played stale output into the headphones, so the operator's P2 "steady beep" may have been the tool. The tool was fixed (silent output, verified by tapping the tool itself: RMS 0) and the confirmation repeated cleanly in P3. The process-tap numbers are unaffected: they measure the app's own output.
